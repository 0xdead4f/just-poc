# SnapShooter — Engagement Report Index

## Executive summary

This engagement against the SnapShooter platform (`app` / `api` / `ingestor` / `agents` / `agent-socket` / `preview`) produced **nine submission-ready reports** spanning one Critical, four High, and three Medium issues. The headline result is a **read-capable Server-Side Request Forgery cluster** rooted in a single reused validator flaw — a "resolve the hostname, check the IP, then never pin it" URL guard that is copy-pasted (or simply omitted) across at least seven URL/host-accepting features. Two reports weaponize that one root cause: F01 demonstrates the SSRF mechanics (DNS-rebind past the guard to AWS IMDS plus a verbatim 4xx/5xx **error**-body read oracle — internal/metadata **reach** but **no sensitive data extracted**, rated **Medium**), and F05 escalates it to **Critical** by exfiltrating real SnapShooter platform secrets — AWS SSM/ECS-Anywhere hybrid-activation credentials and a signed internal ingestor token — out of the company's own DigitalOcean serverless backup fleet to attacker-controlled storage. Alongside the SSRF work, the engagement confirmed a no-CSP stored XSS that executes in a teammate's authenticated session (F02), a fully unauthenticated Stripe webhook with no signature verification (F11), Sanctum API tokens that survive password reset and change (F12), a no-payment paid-plan/compute bypass (F07-F08), and an nginx Basic-auth bypass exposing unauthenticated PHP execution and source disclosure on staging (F04). Every report is severity-matched to what was *demonstrated*, with blocked escalations stated plainly as not-demonstrated rather than claimed.

## SSRF cluster framing (one root cause — do not double-count)

F01 and F05 are **two reports of the same root cause**, not two independent SSRFs: a **reused, non-IP-pinning "resolve-then-check" URL validator**. The guard resolves the supplied hostname, checks the resolved IP against a private/loopback/link-local deny-list, and then never pins it — so the downstream client (AWS SDK / `curl` / `rclone`) re-resolves the same name at connect time, opening a time-of-check/time-of-use DNS-rebind window. The identical pattern is reused or omitted across at least seven URL/host-accepting sinks (storage `endpoint`, storage `region`, developer webhooks, Slack `hook_url`, two SSH test-connection hosts, and the URL-Backup `config.url`), all closed by the **one fix**: resolve once, pin the validated IP, connect to that literal IP, forbid redirects, and block link-local/metadata ranges at egress.

- **F01 is the PoC report** — it establishes the SSRF mechanics on the AWS app backend (`eu-west-1`): DNS-rebind to AWS IMDS (`169.254.169.254`, 403 = IMDSv2), the verbatim 4xx/5xx **error**-body read oracle, a deterministic no-rebind `region` breakout, and the five sibling features as breadth. Rated **Medium** — the demonstrated impact is internal/metadata **reach** + an error-body oracle; **no sensitive data, credential, or cross-tenant data was actually read** (IMDS answered 403; a 200 body is swallowed). IMDSv2 403 + an immovable terminal path suffix + the 4xx-only oracle block any realized-impact High/Critical; "Critical if IMDSv1" is an unmet *if*. (A program that rewards cloud-metadata reach on capability grounds may elevate; we report the demonstrated impact.)
- **F05 is the Critical body-read** — it escalates the *same* flaw on the **DigitalOcean** serverless backup fleet, where the rebind reaches *droplet* metadata (`/metadata/v1/user-data`) and the response body — actual cleartext platform secrets — is exfiltrated to attacker storage. The Critical rests on a genuine on-disk capture, not the F01 IMDS reach.

The two reports are deliberately scoped so impact is **counted once**: F01 owns the IMDS/internal-reach + read-oracle mechanics and the breadth table; F05 owns the captured-secret escalation on the DO egress path. Neither borrows the other's ceiling.

## Backup-recipe injection framing (a second systemic root cause — F13 anchors it)

F13 is one confirmed instance of a second engagement-wide pattern: **secondary free-text fields on backup recipes are passed to the backup tool as raw command-line arguments, bypassing the per-tool flag allowlists** that guard the dedicated `*_flags` fields. The product allowlists `mysql_flags` / `mongodb_flags` / `pg` flags tightly — but the *sibling* fields (`config.flags` on s3-sync, `exclude` / `exclude_paths` / `ingore_tables` on the website/CMS recipes, `export_flags` on TYPO3, `backup_path` / `site_path` / `root_path` on the local-read recipes) are unvalidated and reach `rclone` / `tar` / `restic` / `mysqldump` as bare argv.

- **F13 (reported, High)** is the *exploited* instance — s3-sync's `config.flags` is on a recipe whose serverless run is **functional**, so `--files-from` lands a real arbitrary file read.
- **Latent (not separately reported — Impact Gate fails today):** the same injection is web-layer-proven on the website/CMS recipes — `ghost.exclude` accepts `tar --checkpoint-action=exec=<cmd>`, `gridpane.exclude_paths` accepts `--use-compress-program=<cmd>` (both arbitrary **command execution** flags), `craft.ingore_tables` smuggles `mysqldump` flags past the allowlist, and 11 recipes accept an unjailed absolute `*_path`. These persist verbatim through `save()` but are **currently un-exploitable only because those recipes' serverless runs are broken** (they upload zero artifacts; a functioning control run on s3-sync/url-backups proves the pipeline, not the recipe). **If SnapShooter fixes those runs, the tar/restic recipes become remote code execution on the backup compute** — the recommendation in the F13 report covers all of these fields, not just `config.flags`. This latent surface is documented for the program as defense-in-depth even though no live impact is claimed.

## Confirmed primitives / gadget shelf

Reusable primitives recovered and verified during the hunt, available to seed future chains:

- **Agent WS protocol + root-RCE exec model (G33 / G36)** — the complete client-side protocol of the SnapShooter backup agent, decompiled from the public unstripped Go binary (header-based WS authorizer, Event JSON schema, root-exec model, `ingestor`/`agent-socket` endpoints, no hardcoded secrets). **The cross-tenant rebind escalation is RULED OUT** (G38): the unvalidated `x-force-client-id` handshake header is accepted but is a **routing no-op** — it does not rebind job dispatch (routing follows the Bearer token's agent), so the foreign-id cross-tenant root-RCE lever does not exist.
- **Sanctum token = full `/v1` API (G42)** — any user can mint an All-scope personal-access token; it reads the entire `/v1` surface but carries **no account-critical mutation route** (no email/password/owner/role/billing write; `app/settings/*` rejects Bearer), so token-only ATO is ruled out. This is the persistence primitive behind F12.
- **S3 supply-chain landing site (G35)** — the agent install/artifact origin bucket (`agent.snapshooter.com`, `eu-west-1`, acct `655017121718`) is mapped as the supply-chain RCE landing site (install one-liner runs as root on every agent host). Current write-posture: **NOT attacker-writable** — tampering is ruled out today, but it is the pre-positioned target the moment any AWS-credential leak (e.g. an `s3:PutObject` cred for that bucket) lands.

## Operator-unblock-gated opportunities

Prioritized escalations that are confirmed-blocked only by a tooling/identity gate the operator can lift — each would harden an existing report or open a new one:

1. **A 2nd verified account** (highest leverage). Unblocks F02's missing **captured cross-user render** — turning the structurally-proven team-scoped stored XSS into an airtight, callback-backed High — and unlocks **L28 cross-tenant BOLA** on the `/v1` nested-jobs surface. The blocker is server-enforced reCAPTCHA v2 on `/register` (and the invite-accept flow routes through the same wall, L23/G45); no OAuth/API signup exists.
2. **Restore Burp / CDP cross-origin read.** Lands F11's realized **free-premium dollar-flip** — the only missing primitive is the account's own `cus_*`, which is exposed solely in the cross-origin `checkout.stripe.com` / `api.stripe.com` response body. A working proxy or Chrome DevTools cross-origin read (an attacker reads their own checkout trivially) drops it straight into the already-proven forged webhook event.
3. **A Laravel `APP_KEY`.** Revives **L29 / L31** — the ingestor AWS-Anywhere signed-API forge chain and the backup/restore BOLA — by enabling forgery of signed ingestor call-home / read-route requests.

Note: **F02 / L37 blind-XSS beacons are planted and actively monitored** against browser-deliverable collectors (re-planted to keep the panel current). If a teammate or SnapShooter staffer organically renders one, it fires a non-self callback that would upgrade F02 to a captured cross-user render with no further operator action.
